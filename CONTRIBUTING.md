# Contributing to qrsalvage

## Your first hour

The map of the whole system is one page: [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md) —
data flow, reading order, the three invariants, and a "where do I change…" table. The method
itself is explained, with figures computed from the real code, on the `/method` page of the
local interface. Read those two and you know where everything lives; the *why* of each
decision is in the docstring of the module it concerns.

Then see it work:

```
git clone https://codeberg.org/Shades_Maverick/qrsalvage
cd qrsalvage
python -m venv .venv
pip install -r requirements.txt && pip install -e .

qrsalvage solve fixtures/engraved-curved-hard.png   # a recovery, narrated in numbers
qrsalvage serve                                     # the same thing with a live view
python scripts/difficulty.py --axis contrast --samples 8   # how claims get measured here
```

Python 3.11 or newer. The checks that gate every change:

```
ruff check . && ruff format --check .
mypy                        # the core requires complete signatures
pytest                      # everything, a couple of minutes
pytest -m "not regression"  # fast path
```

The tests double as the specification — they are named as claims
(`test_scattered_erasures_reach_what_no_prefix_can`) and reading the ones around your change
is the fastest way to learn what behaviour is load-bearing. The measurement instruments in
`scripts/` have their own index: [`scripts/README.md`](scripts/README.md).

## Three rules that are not negotiable

**No real photographs in the repository.** The corpus in `fixtures/` is synthetic and
regenerated by `python scripts/make_fixtures.py`. Real photographs of damaged QR codes are
almost always personal — they show hands, rooms, equipment labels — and the decoded content is
frequently a secret, such as a device pairing code. If you have a photograph that qrsalvage
fails on, describe the damage and reproduce it with `qrsalvage synth` and the `Damage`
parameters. That makes it a test case everyone can run.

**A recovered payload is not yours to publish, and least of all when the photograph was not
yours either.** People post pictures of unreadable codes asking for help, which makes them
excellent test material and does not make the device yours. A Zigbee install code or a Matter
onboarding payload is a pairing secret, not an identifier: whoever has it and is within radio
range can join or impersonate that device. If you recover someone's code, give them the device
address they asked for and send the secret privately. `scripts/add_private_fixture.py` takes
`--third-party` and `--provenance` so a local fixture carries that warning with it.

**A cell has three states.** Dark, light, and unknown. Never reduce that to two, not even "for
simplicity" in an intermediate layer. Reed-Solomon repairs twice as many erasures as errors, so
discarding uncertainty throws away half the leverage of the whole project.

**No network access at runtime.** Not in the core, not in any interface. Images and decoded
payloads never leave the machine.

## Changes to the recovery path have to be measured

```
python scripts/difficulty.py --axis contrast    # before
# ... your change ...
python scripts/difficulty.py --axis contrast    # after
```

Quote both in the pull request. "This should be better now" is not reviewable, and the project
has the tooling to do better than that.

Two things to keep in mind when reading those numbers:

- **Rates need intervals.** The script prints Wilson confidence intervals for a reason. With
  twelve samples, an improvement from 8 % to 33 % is not distinguishable from noise. If your
  change is subtle, raise `--samples` rather than declaring victory.
- **`known cells wrong` is the honest metric for sampling changes.** Whether a particular image
  decodes is close to a step function; the number of wrongly sampled known cells is continuous
  and moves before the success rate does.

## Negative findings stay in the code

`src/qrsalvage/core/ensemble.py` contains two approaches that sounded plausible and demonstrably
achieved nothing, documented with the measurements that killed them. They are off by default and
they stay, so nobody invents them again.

If your idea does not work, a pull request that documents *why* — with numbers — is worth as
much as one that adds a feature. Please do not delete such a record to make the module tidier.

## Style

- Everything in the code is English: identifiers, docstrings, comments, test names and program
  output.
- Module coordinates are `(row, col)` with the origin at the top left; pixel coordinates are
  `(x, y)`. Confusing the two is the most likely source of error in this project.
- Docstrings explain *why*, not *what*. The what is in the code below them.
- The core under `src/qrsalvage/core/` imports no CLI, server or UI code and prints nothing. All
  reporting belongs to the caller.

## Scope

qrsalvage handles QR Code only. Data Matrix, Aztec and PDF417 share the philosophy but each
needs its own structure model, placement order and Reed-Solomon parameters — that is a new
module, not a parameter. The symbology-specific parts are already isolated in `structure.py`,
`layout.py` and `qrspec.py`; everything else is symbology-agnostic. If you want to add one,
open an issue first so the boundary can be agreed on before the work starts.
